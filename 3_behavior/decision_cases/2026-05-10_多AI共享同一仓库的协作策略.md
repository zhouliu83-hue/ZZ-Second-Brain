# 决策：两个 AI 同时往一个仓库写，选了"先跑起来，出问题再调整"

## 情境

WorkBuddy 也接入了同一个 GitHub 仓库（当时的 `my-ai-os`）。
两个 AI 助手会同时往这个仓库 push 内容。约束很现实：
没有专职运维，没有协调服务，也没有人 24 小时盯着冲突。

## 我看到的信号

- 两个 AI 同时 push 会产生 git 冲突，而且冲突解法需要判断力，自动化不了
- 同一次对话可能被两个 AI 各记一遍，产生重复内容
- 两边的分类标准不一致，A 认为是洞察的东西 B 可能存进 behavior

## 我的判断

这三个问题的**解法成本不对称**。

按严重程度排：冲突 > 重复 > 分类不一致。
但按**发生频率**排反过来：分类不一致每次都发生，冲突可能一个月才一次，重复更是偶发。

而冲突恰恰是最贵的——它需要人介入。
所以正确做法不是"提前解决所有问题"，而是"先解决最贵的那个"，
剩下的靠观察补。

## 三个选项

| 选项 | 我的看法 |
|------|---------|
| A. 文件名加 AI 标识区分来源 | 解决重复，不解决冲突。而且文件名变难看，以后要清理 |
| B. 建立完整协同机制（锁、分工、约定） | 成本最高，但问题还没实际发生。属于过度设计 |
| C. 先跑起来看看，出问题再调整 | 零成本。冲突真发生时，才知道该加什么锁 |

## 我选了 C

理由：**在没有真实冲突样本的情况下设计协调机制，等于猜。**
不如让它跑，真出事再看。

同时定了两条底线：
- push 前先 pull
- 有价值的对话才上传，水文不上传

## 被否掉的方案 + 为什么否

**否掉 B（完整协同机制）**，这是本次决策最重要的一条。

理由：机制应该由问题驱动，不由焦虑驱动。
在没有冲突样本时定规则，多半会定出一堆用不上的规则，
还给自己增加维护负担——这正是 `1_identity/values.md` 里说的"装"。

**没有否掉 A，而是推迟。** A 解决的是重复，重复的解法（文件名加标识）
如果真要做，仍然可以做，它不构成前置依赖。

## 预期结果

短期内会有零星冲突，但都能靠"先 pull"消掉。
分类不一致会存在但不致命。

## 实际结果

**2026-10-12 回看，验证如下：**

- 冲突：未发生。15 次提交线性，无merge，无冲突记录。
- 重复：未发现。内容无明显重复条目。
- 分类不一致：**已发生**，但表现不是预想的那种——
  没有出现"同一洞察被存进两个目录"，而是出现了**更根本的问题**：
  沉淀机制整体没启动（`6_memory/insights` 只有 3 条，
  `decision_cases`、`failures`、`benchmark_outputs` 全空）。

也就是说：当时判断的三档风险里，
真正的高频风险不是 A、B、C 任何一个，
而是**"根本没东西可写"**——这一档当时没有列进选项。

## 教训

1. **选 C 是对的。** 零成本先跑，验证了 A、B 确实不是瓶颈。这个决策本身没问题。
2. **但选项清单本身有缺口。** 制定选项时漏了最可能的那一档——
   "根本没有沉淀机制"。风险清单的完备性，比风险本身更重要。
3. **"出问题再调整"的前提是问题会自己冒出来。**
   如果问题不会冒出来（因为压根没有数据流），那这个策略就是无限期搁置。
   一年后回头看，它不是"没问题"，是"没开始"。

   → 这条已经转化为系统改动：见 `tools/evolve.py`，
   把"有没有在沉淀"变成可查的数字，而不是靠感觉。

## 可复用模式

**做决策时，先问"我列的这一档是不是真的最高频"。
如果所有选项都是"出问题后再修"类，
说明真正的风险还没被看见。**
